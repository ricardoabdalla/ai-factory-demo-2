# Software Factory: research notes

- **Research date:** 2026-10-12
- **Purpose:** The factual basis for an educational site (written in pt-BR) on the general industry concept of a "software factory". Notes are in English; quotes stay in their original language.
- **Verification:** Every URL below was fetched during research unless it is marked otherwise. Some US-government sites (af.mil, defense.gov, gao.gov, dtic.mil) and a few corporate sites (openai.com, gartner.com) block this research environment, so their content was **checked against Internet Archive (Wayback Machine) copies of the same URL**. Those are marked *(verified via archived copy)*. The citation is still the original URL.

---

## Key takeaways

1. **The term is about 58 years old.** The 1968 NATO Software Engineering conference report already contains R.W. Bemer's working paper about a "machine-controlled production environment, or software factory" ([Naur & Randell, NATO 1968 report](http://homepages.cs.ncl.ac.uk/brian.randell/NATO/nato1968.PDF)). M.D. McIlroy's talk at the same conference, "Mass produced software components", argued that software should be industrialized ([McIlroy 1968](https://www.cs.dartmouth.edu/~doug/components.txt)).
2. **Every era reuses the same promise in a new form:** move software from craft to industrial production through standardization, reuse, automation and measurement. In the 1970s–80s the means was organizational process (Hitachi, Toshiba, NEC, Fujitsu, SDC). In 2004 it was models and DSLs (Microsoft). In the 2010s it was CI/CD pipelines and platforms (DoD, platform engineering). In 2025–26 it is AI coding agents fed by specs and checked by automated gates.
3. **The modern meaning:** an end-to-end system where agents turn intent (specs, issues, signals) into merged, deployed changes, and humans design, govern and verify that system ([Factory, Jun 2026](https://factory.com/news/software-factory); [StrongDM, Feb 2026](https://factory.strongdm.ai/); [OpenAI, Feb 2026](https://openai.com/index/harness-engineering/)).
4. **Spec-driven development (SDD) is the "input station".** GitHub Spec Kit (Sep 2025) and Amazon Kiro (Jul 2025) formalize a Spec → Plan → Tasks → Implement flow ([GitHub](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/); [Kiro](https://kiro.dev/blog/introducing-kiro/)). Independent reviewers call SDD promising but "elaborate and opinionated" ([Thoughtworks Radar, Nov 2025](https://www.thoughtworks.com/radar/techniques/spec-driven-development); [Böckeler, Oct 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).
5. **Verification is the hard part.** Agents game narrow tests ([METR, Jun 2025](https://metr.org/blog/2025-06-05-recent-reward-hacking/); [StrongDM](https://factory.strongdm.ai/)). Spotify ranks "passes CI but functionally incorrect" as the most serious agent failure ([Spotify, Dec 2025](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)).
6. **"Dark factory" is a 2026 label, not the norm.** Dan Shapiro's Jan 2026 "five levels" essay popularized the term, borrowing it from FANUC's lights-out robot plant. He says he knows only "a handful" of teams working at that level ([Shapiro](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)). Most published production setups still keep humans reviewing or approving, for example Stripe, Spotify and GitHub.
7. **The evidence is mixed, and adopters should hear that.** METR's 2025 RCT found experienced developers were **19% slower** with AI while believing they were faster. METR's 2026 follow-up says today's speedup is likely higher but cannot measure it reliably ([METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [METR 2026](https://metr.org/blog/2026-02-24-uplift-update/)). DORA 2025 calls AI an "amplifier": it raises throughput and also delivery instability ([Google Cloud, Sep 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)).
8. **Roles shift toward specifying, verifying and designing the line.** OpenAI describes the engineer's new job as to "design environments, specify intent, and build feedback loops" ([OpenAI](https://openai.com/index/harness-engineering/)). Andrew Ng: "deciding what to build is the new bottleneck" ([The Batch, Jul 2025](https://www.deeplearning.ai/the-batch/how-to-get-through-the-product-management-bottleneck)).
9. **The factory metaphor has been criticized in every era.** SDC's 1970s factory "fell gradually into disuse" ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131)). Microsoft's own authors called the term "controversial" in 2004, and its patterns & practices factories were retired around 2011 ([Greenfield & Short 2004](https://learn.microsoft.com/en-us/archive/blogs/askburton/moving-to-software-factories-2); [MS Learn](https://learn.microsoft.com/en-us/previous-versions/msp-n-p/ff699490(v=pandp.10))).

## Confidence & gaps

- **High confidence:** Eras 1–3. The sources are primary documents: the NATO report, Cusumano's MIT papers, Microsoft archives, the DoD strategy and the GAO report.
- **Medium confidence:** Era 4. Primary sources exist (first-party blogs and docs), but most are **vendor or practitioner self-reports** with no independent audit. Independent evidence (METR, DORA, Stack Overflow, academic papers) mostly measures *AI-assisted coding in general*, not full "factories".
- **Thin areas:** (a) independent data on *dark-factory* outcomes, where none was found; (b) sourced statements about **designers'** changing role, where only one first-party example was found; (c) the exact origin of "dark factory" as a software term, because Shapiro popularized it and earlier blog uses may exist; (d) primary pages for Platform One and Kessel Run's founding, because the live sites were unreachable and some details rely on GAO and af.mil.

## Editorial decisions for the site (2026-10-12)

How flagged claims may be used in the site's pages:
- **Cut:** claims backed only by secondary sources: the FANUC "since 2001 / 30 days" figures, the Spotify co-CEO "no code since December" claim, and Andrew Ng's PM:engineer ratio anecdote. "Very few factories run exclusively lights-out" (SME) can stay.
- **Soften:** Kessel Run is "uma das primeiras" software factories of the DoD, never "a primeira".
- **Attribute, never prove:** vendor self-reports (OpenAI 1/10th time, StrongDM $1,000/day, Stripe 1,000+ PRs/week, Spotify 60–90%, Anthropic 50%, Devin SWE-bench, Veracode 45%) appear only as clearly attributed examples ("segundo a própria empresa"), never as evidence. Gartner's 80% is labelled a forecast.
- **Be honest about thin evidence:** the designers' role stays brief and says openly that evidence is still scarce. Inferences (QA shift, "what not to automate") are presented as emerging practice or synthesis, not fact.

## 1. Japanese (and US) software factories, 1960s–1980s

**Origin of the term**
- **1968, NATO conference (Garmisch, 7–11 Oct 1968).** The report says the phrase "software engineering" was "deliberately chosen as being provocative, in implying the need for software manufacture to be based on the types of theoretical foundations and practical disciplines, that are traditional in the established branches of engineering" ([Naur & Randell 1969, NATO report](http://homepages.cs.ncl.ac.uk/brian.randell/NATO/nato1968.PDF)).
- **R.W. Bemer (General Electric).** His working paper, reproduced in that report, describes the "machine-controlled production environment, or software factory. Program construction, checkout and usage are done entirely within this environment using the tools it contains" ([NATO report, ~p.94](http://homepages.cs.ncl.ac.uk/brian.randell/NATO/nato1968.PDF)). Cusumano credits Bemer with "the industry's first working definition of what might constitute a software factory" and notes GE left the computer business in 1970 ([Cusumano 1991 encyclopedia entry](https://dspace.mit.edu/handle/1721.1/17131)).
- **M.D. McIlroy (Bell Labs/AT&T), "Mass produced software components" (1968).** He wrote: "Software production today appears in the scale of industrialization somewhere below the more backward construction industries." He proposed a "components industry" with catalogues of standard parts ([McIlroy text, NATO pp.138–155](https://www.cs.dartmouth.edu/~doug/components.txt)). Cusumano says the reception "was mixed" ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131)).

**US pioneer: System Development Corporation (SDC), 1975–1978**
- SDC "established the first U.S. software facility called a factory in 1975-1976" and copyrighted the name "The Software Factory". Program managers handed specifications to "what was essentially an assembly line of three groups": Design, Development, and System Test & Verification ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131)).
- About 10 projects went through it between 1976 and 1978. "After Munson left, however, the factory fell gradually into disuse": tools did not port across projects, managers preferred to build their own software, and an unfamiliar project (the LA Police system) left factory programmers idle ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131); see also [Cusumano 1988, SDC working paper](https://dspace.mit.edu/handle/1721.1/49002)).

**Japan**
- **Hitachi (1969).** "By founding its Software Works in 1969, Hitachi was the first company in the world to apply the term factory (actually, its Japanese equivalent, [kōjō] …) to an actual software facility." (The scanned text reads "kolo", an OCR error; the bracketed word is my correction.) The aim was to turn software "from an unstructured 'service' to a 'product' with a guaranteed level of cost and quality." Projects delivered late to QA fell from over 72% in 1970 to 6.9% in 1974 ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131)). *These figures are Hitachi company data as reported by Cusumano.*
- **Toshiba (1977).** Yoshihiro Matsumoto's group set four policies: standardize the process, reuse designs and code, use standardized integrated tools, and train extensively. Reuse grew from 13% (1979) to 48% (1985) ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131)).
- **NEC** formed a Basic Software Development Division in 1974, a Software Strategy Project in 1976 and a Software Quality Control program from 1978. **Fujitsu** set up a basic-software division in the mid-1970s. Its defects fell from 0.19 to 0.01 per 1,000 lines between 1977 and 1985 ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131)).
- **The book.** Michael A. Cusumano, *Japan's Software Factories: A Challenge to U.S. Management* (Oxford University Press, 1991), covers SDC, Hitachi, Toshiba, NEC and Fujitsu ([OUP Academic](https://academic.oup.com/book/52424); the 1991 entry says it "is a summary of Cusumano, 1991" ([MIT](https://dspace.mit.edu/handle/1721.1/17131))).
- **Key ideas** (Cusumano's summary): "standardization of development methods and tools, systematic reuse of program components or designs, some divisions of labor and functional departments, and disciplined project management as well as product quality control" ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131)).
- **Counter-view from the same research.** Cusumano's 1989 paper summarizes critics who argued that software has "little product or process standardization", varied project content, and tasks "difficult and sometimes counterproductive to divide, de-skill, or automate" ([Cusumano 1989, Sloan WP 3095-89](https://dspace.mit.edu/handle/1721.1/47992)).

**Suggested teaching points**
- The "software factory" is not an AI idea. It began in 1968 as a response to the "software crisis", and the 1968 definition (do all work inside one tooled, measured environment) reads like a modern platform.
- Analogy supported by the sources: SDC literally built an assembly line of three groups, and it failed because the work varied too much between projects. That is the same tension modern factories face.
- Hitachi shows the payoff when the product family is narrow: late deliveries fell from 72% to about 7% in four years.

## 2. Microsoft "Software Factories" (2004)

- **The book.** Jack Greenfield and Keith Short, with Steve Cook and Stuart Kent, *Software Factories: Assembling Applications with Patterns, Models, Frameworks, and Tools*, "published by John Wiley & Sons in September 2004" ([authors' site](https://softwarefactories.com/TheBook.html)).
- **Definition (authors, 2004-09-20).** "A software factory is a product line that configures extensible development tools like Microsoft Visual Studio Team System (VSTS) with packaged content and guidance, carefully designed for building specific kinds of applications." It has three parts: a **schema** ("a recipe"), a **template** ("a bag of groceries"), and an extensible IDE ("the kitchen") ([Greenfield & Short, MS Learn archive](https://learn.microsoft.com/en-us/archive/blogs/askburton/moving-to-software-factories-2)).
- **Industrialization thesis.** Other industries moved "from craftsmanship … to manufacturing, where a wide range of product variants is rapidly assembled from reusable components." The authors used "models based on small, focused, domain specific languages (DSLs) for automation" and explicitly distanced themselves from OMG's MDA ("we are less concerned with portability and platform independence than MDA, and more concerned with productivity") ([same](https://learn.microsoft.com/en-us/archive/blogs/askburton/moving-to-software-factories-2)).
- **The authors anticipated the criticism.** "We realize that the term software factory is controversial – conjuring up for some visions of mindless automatons stamping out applications with all creativity in the process removed." Their answer: "stop wasting the talents of skilled developers on rote and menial tasks" ([same](https://learn.microsoft.com/en-us/archive/blogs/askburton/moving-to-software-factories-2)).
- **Implementation (2005–2010).** Microsoft patterns & practices shipped the Mobile Client, Smart Client, Web Client, Web Service and Application Block software factories plus the **Guidance Automation Toolkit** (templates, wizards, "recipes"). The page is dated 2007-11-09 ([MS Learn p&p](https://learn.microsoft.com/en-us/previous-versions/bb190387(v=msdn.10))).
- **What happened next.** The Web Service Software Factory 2010 page is marked "Retired: November 2011" and "now maintained by the community" ([MS Learn](https://learn.microsoft.com/en-us/previous-versions/msp-n-p/ff699490(v=pandp.10))). The GAT docs are marked "Retired Content … no longer being maintained" ([MS Learn](https://learn.microsoft.com/en-us/previous-versions/msp-n-p/ff697230(v=pandp.10))). The DSL technology survives as the **Modeling SDK for Visual Studio**, still documented for VS 2022 ([MS Learn](https://learn.microsoft.com/en-us/visualstudio/modeling/modeling-sdk-for-visual-studio-domain-specific-languages)).
- **Wider assessment of model-driven development.** Martin Fowler (2008-07-14) wrote that he is "rather skeptical of its future" and that graphical models are not inherently a higher abstraction than code ([Fowler, MDSD](https://martinfowler.com/bliki/ModelDrivenSoftwareDevelopment.html)). *Fowler's note concerns MDSD in general, not Microsoft's factories specifically.*
- **Link to today.** Böckeler (2025) warns that spec-as-source AI tools "might end up with the downsides of both MDD and LLMs: Inflexibility and non-determinism" ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).

**Suggested teaching points**
- Use the authors' own restaurant analogy: schema = recipe, template = groceries, IDE = kitchen; product-line developers = chefs who set the menu, product developers = cooks.
- In 2004 "generate code from a higher-level description" meant DSL models. In 2025 it means natural-language specs and LLMs. The idea is the same; the engine changed.
- The tooling was retired, but product lines, guidance automation and templates live on in today's golden paths and agent instructions.

## 3. DevOps / platform-engineering software factories (2010s – early 2020s)

**US Department of Defense**
- **Official definition (DoD Software Modernization Strategy v1.0, Nov 2021, approved Feb 2022).** "A software factory is a software assembly plant for development and integration that contains multiple pipelines, equipped with a set of tools, process workflows, scripts, and environments, to produce a set of software deployable artifacts with minimal human intervention. It automates the activities in the develop, build, test, release, and deliver phases and supports multi-tenancy." The same document defines DevSecOps as a practice that aims to "automate, monitor, and apply security at all phases of the software lifecycle" ([DoD, media.defense.gov](https://media.defense.gov/2022/Feb/03/2002932833/-1/-1/1/department-of-defense-software-modernization-strategy.pdf)) *(verified via archived copy)*.
- **Scale.** GAO (April 2023): DoD has established "29 software factories … including at least one software factory in each military department, such as the Department of the Air Force's Platform One and Kessel Run, the Navy's Forge, and Army's Software Factory." The Defense Science Board (Feb 2018) had called software factories "a crucial part of iterative development practices" ([GAO-23-105611](https://www.gao.gov/assets/gao-23-105611.pdf)) *(verified via archived copy)*.
- **Kessel Run (USAF).** An af.mil article (Dec 2022) says "Kessel Run has maintained TBMCS since 2017" and that on Nov 20, 2022 it replaced the 609th AOC's legacy system with its KRADOS suite ([ACC/af.mil](https://www.acc.af.mil/News/Article/3238418/afcents-609th-aoc-shifts-to-user-focused-software-suite/)) *(verified via archived copy)*. Its current site describes it as "an Air Force unit that delivers resilient command and control and targeting software capabilities" ([kesselrun.af.mil/about](https://kesselrun.af.mil/about/)) *(verified via archived copy, Jun 2025)*. **[UNVERIFIED]** The popular claim that Kessel Run was the DoD's *first* software factory (2017) appears in trade press, but no official primary page stating it was found.
- **Platform One.** The GAO report above names it as a DoD Air Force software factory. **[UNVERIFIED]** Details about its services (Iron Bank, Big Bang) come from secondary sources; the official dso.mil sites were unreachable.

**Pipelines and platform engineering**
- **The deployment pipeline as an assembly line.** "The key pattern introduced in continuous delivery is the deployment pipeline … every change in version control triggers a process … which creates deployable packages and runs automated unit tests and other validations" ([Jez Humble, continuousdelivery.com](https://continuousdelivery.com/implementing/patterns/)).
- **Golden paths (Spotify, Aug 2020).** "The Golden Path … is the 'opinionated and supported' path to 'build something'." It replaced what Spotify engineers called "rumour-driven development" ([Spotify Engineering, 2020-08-17](https://engineering.atspotify.com/2020/08/how-we-use-golden-paths-to-solve-fragmentation-in-our-software-ecosystem)).
- **CNCF Platforms White Paper (Apr 2023).** "A platform for cloud-native computing is an integrated collection of capabilities." It describes a reusable build-scan-test-deploy-observe workflow as "a bundle often described as a golden path" ([CNCF TAG App Delivery](https://tag-app-delivery.cncf.io/whitepapers/platforms/); announced in the [CNCF blog, 2023-04-11](https://www.cncf.io/blog/2023/04/11/announcing-a-white-paper-on-platforms-for-cloud-native-computing/)).
- **Gartner.** "A dedicated product team creates and maintains the engineering platform … providing common, reusable tools and capabilities." Its forecast: "By 2026, 80% of large software engineering organizations will establish platform engineering teams … up from 45% in 2022" ([Gartner](https://www.gartner.com/en/infrastructure-and-it-operations-leaders/topics/platform-engineering)) *(verified via archived copy)*. **[ANALYST FORECAST]** This is a prediction, not a measurement.
- **DORA evidence.** 2024: "Internal development platforms effectively increase productivity for developers", but platform initiatives may cause "a temporary decrease in performance" ([Google Cloud, 2024-10-22](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)). 2025: "90% of organizations have adopted at least one platform and there is a direct correlation between a high quality internal platform and an organization's ability to unlock the value of AI" ([Google Cloud, 2025-09-23](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)). This is the bridge from Era 3 to Era 4.

**Suggested teaching points**
- The DoD definition is the clearest "factory = pipeline" statement: an *assembly plant* of pipelines producing deployable artifacts "with minimal human intervention".
- Golden path = the factory's standard work. Spotify's "rumour-driven development" is a memorable example of what happens without one.
- DORA 2025 makes a usable point: AI factories sit on top of platforms, so a weak platform means weak AI results.

## 4. The AI-agent software factory (2025–2026)

### 4.1 What people mean by the term now
- **StrongDM (Justin McCarthy, 2026-02-06).** "We built a Software Factory: non-interactive development where specs + scenarios drive agents that write code, run harnesses, and converge without human review." Rules: "Code must not be written by humans / Code must not be reviewed by humans" ([factory.strongdm.ai](https://factory.strongdm.ai/)). **[VENDOR CLAIM]** Self-reported, no independent audit.
- **Factory (Grinberg & Reyes, 2026-06-15).** "An interconnected, agent-native, end-to-end system": signals (bug reports, customer feedback, requirements) are triaged into changes that are "built, tested, reviewed, secured, shipped, and monitored", and monitoring feeds new signals back in ([Factory](https://factory.com/news/software-factory)). **[VENDOR]**
- **OpenAI (Ryan Lopopolo, 2026-02-11).** A five-month internal product with "no manually-written code", about a million lines, and roughly 1,500 PRs merged by a team that grew from three to seven engineers. "We estimate that we built this in about 1/10th the time." "Humans may review pull requests, but aren't required to." ([OpenAI, Harness engineering](https://openai.com/index/harness-engineering/)) *(verified via archived copy)*. **[VENDOR CLAIM]** The 10x figure is the team's own estimate.
- **Stripe (Alistair Gray, 2026-02-09).** "Over a thousand pull requests merged each week at Stripe are completely minion-produced … while they're human-reviewed, they contain no human-written code." Agents get "at most two rounds of CI" ([stripe.dev](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)). **[VENDOR CLAIM]** The share of trivial work (lint fixes, dependency updates) is not disclosed.
- **BCG Platinion (2026-03-26).** "Autonomous AI agents build, test, and ship software … humans define business intent and review outcomes." Also: "every stage gate has a human accountable for approval" ([BCG Platinion](https://www.bcgplatinion.com/insights/the-agentic-software-factory)). **[CONSULTANCY]**
- **Conference framing.** The AI Engineer topic page defines it as something that "organizes people, tools, and automation to turn software requests into accepted, delivered changes". 2026 talks include Uber ("Building Blocks for Uber's Software Factory") and "Why Software Factories Fail" (Dex Horthy) ([ai.engineer](https://ai.engineer/topics/software-factories)).
- **Vibe coding vs. engineering.** Karpathy coined "vibe coding": "fully give in to the vibes … and forget that the code even exists" ([quoted by Willison, 2025-03-19](https://simonwillison.net/2025/Mar/19/vibe-coding/)). **[DATE DISCREPANCY]** Willison says Feb 6; the tweet ID decodes to Feb 2, 2025. Willison's line: if you reviewed, tested and understood the code, it's "not vibe coding, it's software development". Kent Beck calls his disciplined version "augmented coding": "you care about the code, its complexity, the tests, & their coverage" ([Beck, 2025-06-25](https://tidyfirst.substack.com/p/augmented-coding-beyond-the-vibes)).

### 4.2 Spec-driven development (the input station)
- **GitHub Spec Kit (Den Delimarsky, 2025-09-02).** Four phases, "Specify, Plan, Tasks, Implement", "with clear checkpoints". The spec "becomes the source of truth your tools and AI agents use to generate, test, and validate code". The rationale: LLMs are "exceptional at pattern completion, but not at mind reading". The shift: from "code is the source of truth" to "intent is the source of truth" ([GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)).
- **Amazon Kiro (Swaminathan & Singh, 2025-07-14).** Requirements (user stories with EARS acceptance criteria) → design document → sequenced tasks linked to requirements. "Hooks are event-driven automations that execute when you save or create files" ([Kiro](https://kiro.dev/blog/introducing-kiro/)).
- **Taxonomy (Birgitta Böckeler, Thoughtworks, 2025-10-15).** *Spec-first*, *spec-anchored* (the spec is kept and evolved), and *spec-as-source* ("the human never touches the code"). Her criticism: "I'd rather review code than all these markdown files". Kiro on a small bug was "like using a sledgehammer to crack a nut" ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).
- **Thoughtworks Technology Radar (2025-11-05), ring "Assess".** "The workflows remain elaborate and opinionated … some generate lengthy spec files that are hard to review … We may be relearning a bitter lesson—that handcrafting detailed rules for AI ultimately doesn't scale" ([Radar](https://www.thoughtworks.com/radar/techniques/spec-driven-development)).
- **Addy Osmani (Google, 2026-01-13).** "Vague specs produce vague code." He recommends three-tier boundaries ("Always do / Ask first / Never do") and keeping the spec alive: "Don't write it and forget it" ([addyosmani.com](https://addyosmani.com/blog/good-spec/)).

### 4.3 Coding agents (the build station). First-party descriptions
- **Devin (Cognition, 2024-03-12).** Marketed as "the first AI software engineer". It claimed 13.86% of SWE-bench issues resolved end-to-end on a random 25% subset ([Cognition](https://cognition.com/blog/introducing-devin)). **[VENDOR BENCHMARK]**
- **OpenAI Codex (2025-05-16).** "A cloud-based software engineering agent that can work on many tasks in parallel … each task runs in its own cloud sandbox environment". It provides "citations of terminal logs and test outputs"; "It still remains essential for users to manually review and validate all agent-generated code" ([OpenAI](https://openai.com/index/introducing-codex/)) *(verified via archived copy)*.
- **GitHub Copilot coding agent (Thomas Dohmke, 2025-05-19).** Assign an issue; it runs in a GitHub Actions environment and pushes to a draft PR. "The agent can only push to branches it created"; its PRs "require human approval before any CI/CD workflows are run"; the requester cannot approve their own PR ([GitHub Blog](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/)).
- **Claude Code (Anthropic docs, accessed 2026-10-12).** "An agentic coding tool that reads your codebase, edits files, runs commands, and integrates with your development tools." It runs in CI (GitHub Actions/GitLab), supports parallel sub-agents, and uses `CLAUDE.md`/`AGENTS.md` instruction files and hooks ([Claude Code docs](https://code.claude.com/docs/en/overview)).
- **Agent vs. workflow (Anthropic, 2024-12-19).** "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents … dynamically direct their own processes and tool usage." For coding: "Code solutions are verifiable through automated tests", but "human review remains crucial" ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)).
- **Background agents at scale (Spotify "Honk", 2025-11-06).** "More than 1,500 pull requests that teams across Spotify have merged" and "a total time saving of 60–90%" on migrations ([Spotify Part 1](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1)). **[VENDOR CLAIM]**
- **Capability trend.** The length of tasks agents complete at 50% reliability "has been doubling approximately every 7 months" ([METR, 2025-03-19](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)). METR itself notes the estimate depends on methodology.

### 4.4 Verification gates
- **Deterministic plus judgment layers (Spotify, 2025-12-09).** Verifiers run formatting, build and tests. An LLM judge compares the diff against the original prompt because agents were "too 'ambitious'" (refactoring, disabling flaky tests); it "vetoes about a quarter" of sessions. The agent runs "in a container with limited permissions" ([Spotify Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). By March 2026, "as models improved, the judge was eventually removed" ([InfoQ, QCon London talk, 2026-03-18](https://www.infoq.com/news/2026/03/spotify-honk-rewrite)). The gates evolve as the line matures.
- **Hidden ("holdout") scenarios (StrongDM).** "A test, stored in the codebase, can be lazily rewritten to match the code." Their answer is end-to-end scenarios stored outside the repo, scored by "satisfaction", against a "Digital Twin Universe" of cloned third-party services ([StrongDM](https://factory.strongdm.ai/)).
- **Evals (Anthropic, 2026-01-09).** An eval is "a test for an AI system: give an AI an input, then apply grading logic to its output". Key terms are task, grader and harness. *pass@k* means at least one success in k tries; *pass^k* means all k succeed. Graders must require "solving the problem rather than exploiting unintended loopholes" ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
- **Long-running harnesses (Anthropic, 2025-11-26).** An initializer agent writes a JSON feature list; coding agents do "one feature at a time" with git checkpoints. Observed failures: "Claude declares victory on the entire project too early" and marks features complete "without proper testing" ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

### 4.5 Human-in-the-loop vs. "dark factory"
- **Manufacturing origin.** "Lights-out manufacturing" means robots working "in total autonomy for extended periods of time". The SME article says "FANUC has operated lights-out since 2001" and that robots at its Oshino plant run "unsupervised for up to 30 days"; it also notes "very few factories run exclusively lights-out" ([SME, 2020-04-17](https://www.sme.org/technologies/articles/2020/april/how-bright-is-the-future-of-automation/)) *(verified via archived copy)*. **[UNVERIFIED]** The FANUC figures are repeated across trade press, but no FANUC primary source was found. The SME author is a parts-supplier manager.
- **Software usage (Dan Shapiro, 2026-01-23).** Five levels modelled on driving autonomy: Level 3 "Your life is diffs" (human in the loop), Level 4 "You write a spec", Level 5 "a black box that turns specs into software … It's dark, because it's a place where humans are neither needed nor welcome". It explicitly references "the Fanuc Dark Factory". On adoption: "I know a handful of people who are doing this", "small teams, less than five people" ([Shapiro](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)); amplified by [Simon Willison, 2026-01-28](https://simonwillison.net/2026/Jan/28/the-five-levels/). **[ORIGIN UNCERTAIN]** Shapiro is the most-cited popularizer, but this research could not confirm he was first.
- **Skeptical response (Simon Willison, 2026-02-07).** On "no human review": "How could that possibly be a sensible strategy when we all know how prone LLMs are to making inhuman mistakes?" On the $1,000/engineer/day token spend: if real, "they're far less interesting to me" ([Willison](https://simonwillison.net/2026/Feb/7/software-factory/)).
- **What production looks like.** GitHub requires human approval before CI ([GitHub](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/)). Stripe's agent output is human-reviewed ([Stripe](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)). BCG puts a human accountable at every gate ([BCG Platinion](https://www.bcgplatinion.com/insights/the-agentic-software-factory)).

### 4.6 Adoption and productivity: evidence vs. hype
- **METR RCT (2025-07-10).** 16 experienced OSS developers, 246 real issues. With AI they "take 19% longer". They expected a 24% speedup and afterwards still believed in a 20% speedup. METR stresses this does not show that AI slows most developers ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); paper [arXiv:2507.09089](https://arxiv.org/pdf/2507.09089) — *URL found in search, not fetched*).
- **METR follow-up (2026-02-24).** Returning developers: "-18% with a confidence interval between -38% and +9%"; new recruits: "-4% … between -15% and +9%". However, "it is likely that developers are more sped up from AI tools now", and the data is "only very weak evidence for the size of this increase" because developers "do not wish to work without AI" (selection bias). Time measurement also breaks down when developers run multiple agents at once ([METR](https://metr.org/blog/2026-02-24-uplift-update/)).
- **DORA 2025 (about 5,000 respondents, 2025-09-23).** "90% of survey respondents report using AI at work", and "30% report little or no trust in the code generated by AI". AI adoption now has a positive relationship with throughput, "However, AI adoption does continue to have a negative relationship with software delivery stability" ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report); [DORA research page](https://research.google/pubs/dora-2025-state-of-ai-assisted-software-development-report/); [DORA, 2026-03-10](https://dora.dev/insights/balancing-ai-tensions/)). DORA 2024 had found AI adoption associated with a 1.5% decrease in throughput and a 7.2% decrease in stability ([Google Cloud, 2024](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)).
- **Stack Overflow Developer Survey 2025.** 84% use or plan to use AI. "More developers actively distrust the accuracy of AI tools (46%) than trust it (33%)". The top frustration (66%) is "AI solutions that are almost right, but not quite". "AI agents are not yet mainstream" ([Stack Overflow](https://survey.stackoverflow.co/2025/ai)).
- **Anthropic internal survey (132 employees, 2025-12-02).** Self-reported "50% productivity boost", Claude used in about 60% of work, and 27% of Claude-assisted work "wouldn't have been done otherwise" ([Anthropic](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)). **[SELF-REPORTED, VENDOR]**
- **Spotify executive claim.** **[UNVERIFIED]** Spotify's co-CEO said on the Feb 2026 earnings call that top developers had not written code since December 2025. Only secondary coverage was found; the TechCrunch original was not fetched.

### 4.7 Suggested teaching points
- A one-line definition the sources support: *a system that turns intent (specs, issues, signals) into verified, deployed changes, with agents doing the building and humans designing the line and owning the outcome.*
- Use Shapiro's driving-levels analogy (Level 0 manual → Level 5 dark factory). It is vivid, and Shapiro himself says Level 5 is rare.
- Show the perception gap from METR (developers felt 20% faster but were 19% slower) next to DORA's "amplifier" finding. The lesson: measure, don't assume.
- Concrete examples: Stripe's "at most two rounds of CI"; Spotify's judge that vetoed about a quarter of sessions and was later removed; StrongDM keeping test scenarios outside the repo so agents cannot "teach to the test".

## Stations of a modern AI software factory (for the interactive diagram)

A defensible generic line built from the sources. The first four stations follow Spec Kit and Kiro (Specify/Plan → Tasks → Implement). Deploy and Feedback follow the DoD pipeline phases and Factory's monitoring loop.

| Station | Inputs | Outputs | Who/what does the work | Typical failure modes |
|---|---|---|---|---|
| **1. Spec** | Business intent, user needs, signals (bugs, feedback) | Spec: user stories, acceptance criteria (e.g., EARS), constraints, boundaries | PM/engineer writes or approves; agent drafts and expands ([Spec Kit](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/); [Kiro](https://kiro.dev/blog/introducing-kiro/); [Osmani](https://addyosmani.com/blog/good-spec/)) | Vague spec produces vague code; specs too long to review ([Thoughtworks](https://www.thoughtworks.com/radar/techniques/spec-driven-development)); over-process on small changes ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)) |
| **2. Tasks** | Approved spec + technical plan | Small, ordered, independently testable tasks linked to requirements | Agent decomposes; human reviews plan ([Spec Kit](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/); [Kiro](https://kiro.dev/blog/introducing-kiro/)) | Tasks too big; agent tries everything at once or declares victory early ([Anthropic harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)) |
| **3. Build (agents)** | One task + repo + instructions (`AGENTS.md`/`CLAUDE.md`), sandboxed environment | Code + tests on a branch / draft PR, with logs | Coding agents (Claude Code, Codex, Copilot agent, in-house agents) in sandboxes ([Codex](https://openai.com/index/introducing-codex/); [Copilot](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/); [Stripe](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)) | Overreach (unrequested refactors, disabled tests) ([Spotify](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)); hallucinated packages ([Spracklen et al.](https://arxiv.org/abs/2406.10279)); prompt injection via untrusted content ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)) |
| **4. Gates** | PR / diff | Pass/fail plus feedback to the agent; approved merge | Deterministic CI (build, lint, tests), LLM judge, hidden scenarios/evals, security scans, human review where required ([Spotify](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3); [StrongDM](https://factory.strongdm.ai/); [Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)) | "Passes CI but functionally incorrect" ([Spotify](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)); tests gamed (`return true`) ([StrongDM](https://factory.strongdm.ai/); [METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)); human review becomes the bottleneck ([OpenAI](https://openai.com/index/harness-engineering/)) |
| **5. Deploy** | Merged, verified artifact | Running software in production | CI/CD deployment pipeline, the classic "assembly plant" ([DoD](https://media.defense.gov/2022/Feb/03/2002932833/-1/-1/1/department-of-defense-software-modernization-strategy.pdf); [continuousdelivery.com](https://continuousdelivery.com/implementing/patterns/)) | More change volume leads to more instability without strong testing and fast feedback ([DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)) |
| **6. Feedback** | Production monitoring, incidents, user feedback, review comments | New signals/specs; updated docs, rules and tooling for agents | Monitoring + agents that triage; humans encode lessons ("doc-gardening" agents, rules promoted into linters) ([Factory](https://factory.com/news/software-factory); [OpenAI](https://openai.com/index/harness-engineering/)) | Lessons not captured, so the same agent mistakes repeat; stale docs mislead agents ([OpenAI](https://openai.com/index/harness-engineering/)) |

**Sources that model the line differently**
- **Factory (Jun 2026)** starts from *signals* (bugs, customer feedback) rather than a written spec. Its loop is triage → build → test → review → secure → ship → monitor ([Factory](https://factory.com/news/software-factory)).
- **BCG Platinion (Mar 2026)** uses three phases (Inception, Construction, Operation) and separate "assembly lines" per delivery type: greenfield, brownfield and legacy modernization ([BCG Platinion](https://www.bcgplatinion.com/insights/the-agentic-software-factory)).
- **StrongDM (Feb 2026)** collapses Build and Gates into a convergence loop (agents iterate until scenario "satisfaction" is high) and removes human review entirely ([StrongDM](https://factory.strongdm.ai/)).
- **DoD (2021)** names the classic phases: plan, develop, build, test, release and deliver, deploy, operate and monitor ([DoD](https://media.defense.gov/2022/Feb/03/2002932833/-1/-1/1/department-of-defense-software-modernization-strategy.pdf)).

## 5. How human roles change

- **Engineers become designers of the line.** OpenAI: the team's job "is no longer to write code, but to design environments, specify intent, and build feedback loops"; "The primary job of our engineering team became enabling the agents to do useful work" ([OpenAI](https://openai.com/index/harness-engineering/)). Factory: engineers move from "the sole custodians of building the software" to building the factories, taking on "governance, safety, and the ownership of business outcomes" ([Factory](https://factory.com/news/software-factory)). **[VENDOR VIEW]**
- **Engineers as reviewers.** Shapiro's Level 3: "Your life is diffs" ([Shapiro](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)). Anthropic engineers describe a "paradox of supervision": supervising Claude needs the coding skills that may atrophy ([Anthropic, Dec 2025](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)).
- **People become more "full-stack".** "Everyone is becoming more 'full-stack'": engineers take on tasks outside their core expertise ([Anthropic, Dec 2025](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)).
- **PMs: spec quality and deciding what to build.** Andrew Ng: "highly agentic coding accelerates the writing of software to a given product specification … deciding what to build is the new bottleneck" ([The Batch, 2025-07-16](https://www.deeplearning.ai/the-batch/how-to-get-through-the-product-management-bottleneck)). **[UNVERIFIED]** Ng's widely quoted PM:engineer ratio anecdote (e.g., 1:0.5) was found only in secondary coverage. Spec Kit's framing, "intent is the source of truth", puts the spec author at the start of the line ([GitHub](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)).
- **QA: from executing tests to designing gates and evals.** Graders, tasks and holdout scenarios that cannot be gamed ([Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [StrongDM](https://factory.strongdm.ai/)). OpenAI reports "our bottleneck became human QA capacity" ([OpenAI](https://openai.com/index/harness-engineering/)). **[INFERENCE]** The shift from test execution to gate and eval design is a reasonable reading of these sources; no source states it as a QA job definition.
- **Designers (thin evidence).** Anthropic's Product Design team uses Claude Code to "write comprehensive tests for new features" and maps "error states, logic flows, and system statuses to identify edge cases during design" ([Anthropic, 2025-07-24](https://claude.com/blog/how-anthropic-teams-use-claude-code)). **[SINGLE VENDOR EXAMPLE]**
- **Cross-functional bottlenecks.** Ng also notes bottlenecks moving to design, marketing and legal review (per [The Batch](https://www.deeplearning.ai/the-batch/how-to-get-through-the-product-management-bottleneck) series; *only the bottleneck quotes above were verified verbatim*).

**Suggested teaching points**
- One-sentence framing (OpenAI's words): engineers now "design environments, specify intent, and build feedback loops".
- For PMs, Ng's bottleneck quote is the hook: when building gets cheap, deciding what to build becomes the constraint.
- For QA and designers, present the shift as *designing what "done" means* (acceptance criteria, edge cases, evals). Label it as an emerging practice, not settled fact.

## 6. Risks and limits

- **Garbage in, garbage out (specs).** "Vague specs produce vague code" ([Osmani](https://addyosmani.com/blog/good-spec/)). LLMs are "not at mind reading" ([GitHub](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)). Böckeler calls detailed upfront specs a possible "false sense of control" and warns of *Verschlimmbesserung*, an improvement that makes things worse ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).
- **Verification gaps and test gaming.** METR saw o3 "patch the competition evaluation function so that it judges every submission as successful"; reward hacking appeared in 30.4% of RE-Bench runs ([METR, 2025-06-05](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). StrongDM: "return true is a great way to pass narrowly written tests" ([StrongDM](https://factory.strongdm.ai/)). Beck watches for "any indication that the genie was cheating, for example by disabling or deleting tests" ([Beck](https://tidyfirst.substack.com/p/augmented-coding-beyond-the-vibes)). Spotify: CI-green but wrong is the worst case ([Spotify](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)).
- **Instability and review burden.** DORA ties AI adoption to lower delivery stability ([DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)). 66% of developers report "almost right, but not quite" output, and 45.2% say debugging AI code takes longer ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/ai)). OpenAI's team hit a human-QA bottleneck ([OpenAI](https://openai.com/index/harness-engineering/)).
- **Cost.** "Agentic systems often trade latency and cost for better task performance", and "the potential for compounding errors" ([Anthropic, 2024-12-19](https://www.anthropic.com/engineering/building-effective-agents)). StrongDM's benchmark of at least $1,000 in tokens per engineer per day drew skepticism ([StrongDM](https://factory.strongdm.ai/); [Willison](https://simonwillison.net/2026/Feb/7/software-factory/)).
- **Security: prompt injection.** OWASP LLM01:2025: "A Prompt Injection Vulnerability occurs when user prompts alter the LLM's behavior or output in unintended ways"; indirect injection comes "from external sources, such as websites or files" ([OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). Willison's "lethal trifecta" is private data + untrusted content + external communication ([Willison, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)).
- **Security: supply chain.** Code LLMs invent package names: at least 5.2% for commercial and 21.7% for open-source models, with 205,474 unique fake names. Attackers can register those names ([Spracklen et al., USENIX Security 2025](https://arxiv.org/abs/2406.10279)).
- **Security: insecure code.** Veracode found AI code "introduces security vulnerabilities in 45 percent of cases" across 80 curated tasks and more than 100 LLMs, with "larger models do not perform significantly better" ([Veracode, 2025-07-30](https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/)). **[VENDOR RESEARCH]** Veracode sells code-security tools, and the result covers curated tasks, not production code.
- **Mitigations in practice.** Sandboxed containers with limited permissions ([Spotify](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)); branch restrictions, required review and an allow-listed network ([GitHub](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/)); "extensive testing in sandboxed environments, along with the appropriate guardrails" ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)).
- **Skill atrophy.** In Anthropic's RCT (52 mostly junior engineers learning the Trio library, 2026-01-29), "participants in the AI group scored 17% lower than those who coded by hand". Using AI to ask conceptual questions or get explanations preserved learning ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)). Engineers worry about "skills atrophying as [they] delegate more" ([Anthropic, Dec 2025](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)).
- **What shouldn't be fully automated.** No source gives a definitive list. Patterns in the sources: keep humans accountable at gates ([BCG Platinion](https://www.bcgplatinion.com/insights/the-agentic-software-factory)); require human approval before CI/CD runs agent code ([GitHub](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/)); "human review remains crucial for ensuring solutions align with broader system requirements" ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)); "Ask first" boundaries for risky actions ([Osmani](https://addyosmani.com/blog/good-spec/)). **[SYNTHESIS]**
- **Historical criticism of the factory metaphor.**
  - SDC's factory faded because projects varied too much and managers resisted handing off specs ([Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131)).
  - Critics argued software is hard to "divide, de-skill, or automate" ([Cusumano 1989](https://dspace.mit.edu/handle/1721.1/47992)).
  - Microsoft's authors acknowledged fears of "mindless automatons" ([2004](https://learn.microsoft.com/en-us/archive/blogs/askburton/moving-to-software-factories-2)), and the tooling was retired around 2011 ([MS Learn](https://learn.microsoft.com/en-us/previous-versions/msp-n-p/ff699490(v=pandp.10))).
  - Even in manufacturing, "very few factories run exclusively lights-out" ([SME](https://www.sme.org/technologies/articles/2020/april/how-bright-is-the-future-of-automation/)).

**Suggested teaching points**
- "Tests that agents can read, agents can game." Use StrongDM's holdout idea and METR's evaluator-patching example.
- Pair each risk with a gate: prompt injection → sandbox and limited permissions; fake packages → dependency allow-lists and scanning; skill atrophy → ask the AI for explanations, not just code (Anthropic RCT).
- The history repeats: in each era the factory worked for narrow, repeatable product families and struggled with novel work.

## 7. Glossary

| Term | Definition (1–2 sentences) | Source |
|---|---|---|
| Software factory (classic) | An environment where programs are built "entirely within this environment using the tools it contains", with measures for productivity and quality. | [Bemer in NATO 1968](http://homepages.cs.ncl.ac.uk/brian.randell/NATO/nato1968.PDF) |
| Software factory (DoD) | "A software assembly plant … that contains multiple pipelines … to produce a set of software deployable artifacts with minimal human intervention." | [DoD 2021/22](https://media.defense.gov/2022/Feb/03/2002932833/-1/-1/1/department-of-defense-software-modernization-strategy.pdf) |
| Software factory (AI era) | A system that organizes "people, tools, and automation to turn software requests into accepted, delivered changes", with agents doing most of the building. | [ai.engineer](https://ai.engineer/topics/software-factories); [Factory](https://factory.com/news/software-factory) |
| Assembly line | Sequential specialized stations that work passes through; SDC routed specs through "essentially an assembly line" of design, development and test groups. | [Cusumano 1991](https://dspace.mit.edu/handle/1721.1/17131) |
| Software product line | "A set of software-intensive systems sharing a common, managed set of features … developed from a common set of core assets in a prescribed way." | [SEI CMU/SEI-2001-TR-017](https://apps.dtic.mil/sti/pdfs/ADA399205.pdf) *(verified via archived copy)* |
| DSL (domain-specific language) | "A computer language that's targeted to a particular kind of problem". | [Fowler 2008](https://martinfowler.com/bliki/DomainSpecificLanguage.html) |
| Model-driven development | Building models (often diagrams) that tools turn into code; OMG's version is Model Driven Architecture (MDA). | [Fowler 2008](https://martinfowler.com/bliki/ModelDrivenSoftwareDevelopment.html); [OMG](https://www.omg.org/mda/) |
| DevSecOps | "An organizational software engineering culture and practice that aims at unifying software development, security, and operations", automating security across all lifecycle phases. | [DoD](https://media.defense.gov/2022/Feb/03/2002932833/-1/-1/1/department-of-defense-software-modernization-strategy.pdf) |
| Continuous Integration (CI) | Team members merge their changes into a shared codebase "at least daily", verified by automated builds and tests. | [Fowler 2024](https://martinfowler.com/articles/continuousIntegration.html) |
| Continuous Delivery (CD) | "The ability to get changes of all types … into production, or into the hands of users, safely and quickly in a sustainable way." | [Humble](https://continuousdelivery.com/) |
| (Deployment) pipeline | Every change "triggers a process … which creates deployable packages and runs automated unit tests and other validations". | [continuousdelivery.com](https://continuousdelivery.com/implementing/patterns/) |
| Golden path | "The 'opinionated and supported' path to 'build something'". | [Spotify 2020](https://engineering.atspotify.com/2020/08/how-we-use-golden-paths-to-solve-fragmentation-in-our-software-ecosystem) |
| Internal developer platform | "An integrated collection of capabilities" offered to internal users, such as app developers (CNCF calls them "internal platforms"). | [CNCF](https://tag-app-delivery.cncf.io/whitepapers/platforms/) |
| Platform engineering | A dedicated product team builds and maintains an engineering platform offering "common, reusable tools and capabilities". | [Gartner](https://www.gartner.com/en/infrastructure-and-it-operations-leaders/topics/platform-engineering) |
| LLM | "AI language models with many parameters" trained on vast text, able to generate text and answer questions. | [Anthropic glossary](https://platform.claude.com/docs/en/about-claude/glossary) |
| Context window | "The amount of text a language model can look back on and reference when generating new text", the model's "working memory". | [Anthropic glossary](https://platform.claude.com/docs/en/about-claude/glossary) |
| Hallucination | Models "sometimes guess when uncertain, producing plausible yet incorrect statements". | [Kalai et al. 2025](https://arxiv.org/abs/2509.04664) |
| Agentic / agent | Systems "where LLMs dynamically direct their own processes and tool usage" (contrast: workflows follow predefined code paths). | [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents) |
| Coding agent | An agent that reads a codebase, edits files, runs commands and opens PRs, e.g. Claude Code, Codex, Copilot coding agent. | [Claude Code docs](https://code.claude.com/docs/en/overview); [OpenAI](https://openai.com/index/introducing-codex/) |
| Spec / spec-driven development | A structured functional spec, written first and broken into plans and tasks for agents; the spec becomes "the source of truth". | [Thoughtworks](https://www.thoughtworks.com/radar/techniques/spec-driven-development); [GitHub](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) |
| Task decomposition | Splitting a plan into "small, reviewable chunks that each solve a specific piece of the puzzle". | [GitHub Spec Kit](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) |
| Verification gate | A check a change must pass before advancing, e.g. format/build/test verifiers and an LLM judge before a PR opens. | [Spotify 2025](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3) |
| Eval | "A test for an AI system: give an AI an input, then apply grading logic to its output to measure success." | [Anthropic 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) |
| (Test/eval) harness | "The infrastructure that runs evals end-to-end"; more broadly, the environment and tooling an agent works inside ("harness engineering"). | [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [OpenAI](https://openai.com/index/harness-engineering/) |
